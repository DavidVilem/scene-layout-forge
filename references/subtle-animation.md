# Optional motion after coloring

Only animate when requested. Keep the default illustrated/colored pair unchanged. The chain is illustrated design -> reviewed colored edit -> animation derived from that exact colored image. Never regenerate the scene from the text brief to make a video. Read the colored pixels first and resolve the actual project. No personal references, prior chat, external skill or particular image-to-video vendor is required.

## Plan from the subject

Choose a few meaningful motions, not a mandatory checklist. Record the origin, fixed anchor, depth/occlusion order, motion envelope and what must stay unchanged. Trees may sway at their foliage while trunks remain anchored; clouds move behind buildings; water may ripple within its banks; instruments may glow; a vehicle at idle can emit subtle exhaust only from an identifiable exhaust outlet. Do not add smoke to arbitrary pipes, animate fixed supports, turn tracks without contact logic, or make all scenery pulse. People/cars should move only where paths and layers support it. Static machinery need not move to make an environment feel alive.

Preserve camera, linework, material palette, detailed architecture, annotations, pipe ends, supports and access paths. Mark vulnerable joints, text and foreground occluders in a protected mask. All masks use full source dimensions and source pixel coordinates. Examine motion at extremes and after encoding. A still image does not contain hidden surfaces, temporal geometry, depth or articulated people.

## Select the renderer honestly

`scripts/animation_workflow.py` implements fixed-camera, local compositing with Pillow and NumPy:

- `drift`: one-way displacement over the clip, suitable for small cloud travel within a fixed mask. `breeze`: periodic foliage oscillation around an anchor. Both sample the source through inward-feathered masks. Not whole-person walking, a rolling vehicle, or a full mechanical rotation. The mask boundary is pinned; inspect stretching and doubled edges.
- `light`: local brightness variation. Keep it modest and explain the light source. It is not a physical day/night lighting solver.
- `plume`: staggered periodic, softly fading puffs from a named outlet. Restricted by the mask and protected occluders. This is a simple stylized particle effect, not simulated fluid.
- `sprite`: a full-canvas transparent layer, a reconstructed clean plate and removal mask, with explicit pivot and small rotation/translation. Requires real prepared assets; source cutouts pasted over the original duplicate objects. Use the image-editing tool for extraction/reconstruction when needed, retaining requests and originals. Inspect the clean plate and silhouette before animation. A single sprite can lean, rock, turn or travel on a path; it cannot perform a credible walk cycle. Walking requires prepared registered pose frames with reviewed foot contacts. The local renderer now supports these frames, continuous rotation, forward travel and static foreground occluder masks. Complex skeletal rigging, view changes and mutual moving-object occlusion still require a specialized renderer.

Do not pretend these local effects cover every requested action. When a subject needs skeletal animation, 3D parallax, changing camera orientation, dynamic mutual occlusion or day/night cast shadows, prepare the needed layers/rig or use an available image-to-video backend with the colored PNG as the source and record its exact identity/settings/request. No such backend is bundled. Preserve the same history/review requirements; report unsupported motion honestly. An optional external backend must not replace the original PNGs. Offer or implement a suitable subtle alternative within the brief rather than blocking all animation because walking is unsupported.

## Execute

Use Python 3.11+, existing requirements and optional `requirements-animation.txt`, or an existing `ffmpeg` on PATH. Install dependencies in the user's chosen environment, never package their binaries. No credentials are needed for the local renderer. If unavailable, preserve the pair and the attempted animation history, explicitly mark animation incomplete.

1. Inspect coloreada.png and its neighboring ilustrada.png. For a new run finish the normal pair workflow first. For an existing pair create a continuation linked to its actual prior history when known; never invent a prior validation. Save the user's brief verbatim.
2. Write a JSON plan with `schema_version: 2`, `timeline: "once"` (default) or explicitly justified `"loop"`, and the visual `inventory` described below. Then set `seconds` (default 6, range 2..20), `fps` (default 24), optional full-canvas grayscale `protected_mask`, and `effects`. Every effect has unique `id`, `kind`, `reason`, `anchor`, `occlusion`, `limits`, plus a grayscale `mask` file OR a `polygon` of pixel points. `feather` defaults to 2px and stays inside the mask. Motion uses `dx`/`dy` (pixels), integer `cycles` (default 1), and optional `strength` (0..0.2). Plume also needs `origin`; sprite needs `sprite`, `clean_plate`, `removal_mask`, `pivot`, optional `angle`. Asset paths resolve from the execution working directory; prefer resolved paths at runtime. No media belongs in this package.
3. `prepare(project, colored, plan, brief, parent_history=None)` copies the source pair and masks into a new output/history/animation-* directory, records the renderer/skill hashes and source identities, and validates renderable parameters. Invalid attempts retain failure evidence. No deletion.
4. `render(job)` creates candidate.mp4, retains the encoder request/log, source-frame samples, decoded samples and a contact sheet, decodes the entire video to check frame count/dimensions, reports whether endpoints match (required only for loops) and verifies unchanged pixels outside motion masks before compression. These checks do not establish physical plausibility or beautiful movement. H264 compression can slightly change pixels throughout the encoded frame. Original dimensions are preserved using yuv444p; some hardware players require a separately retained yuv420p compatibility export (pad odd dimensions explicitly, never silently crop).
5. Inspect actual motion, decoded eighth-interval frames including endpoints, and wraparound only when requesting a loop. Forward clips must not reverse for closure. Review source_fidelity, connections, occlusion, motion, loop and style with specific observations, not automatic approval. Status is passed/failed/uncertain. Verify no double limbs/cars, clipping, stretched connections, new labels, texture flicker or incorrect smoke origin. A contact sheet alone cannot prove smooth playback; disclose when temporal inspection is limited.
6. `accept(job, observations)` retains the review and rejects known failures, changed sources/candidate or overwrites, then copies the reviewed candidate to animada.mp4 beside both untouched PNGs. A maximum of two local correction attempts should each use a new job linked to the previous one; retain every attempt. If a video already exists, use a new numbered output folder with byte-identical copies of the pair and record the original lineage. Never overwrite the existing video.

Report all three paths, source dimensions, encoded dimensions, duration, frame rate, implemented motions and remaining uncertainty. Animation is optional: the pair remains a successful image delivery if animation fails. Do not promise that an artistic image or a masked animation simulates loads, fluids, mechanisms or people.


## Visual selection and time laws (revision 21)

Inspect the actual colored image, including small pedestrians/vehicles, and record candidate objects as `inventory` entries with `id`, `category`, `evidence`, `decision` (animate/fixed/deferred), and `reason`. Evidence identifies a visible region and observation, not an invented detection confidence. Each animated effect refers to its `target` inventory ID and matching `category`. All selected targets need effects; deferred actions must be disclosed. The Python validator checks this contract; the executing vision-capable agent performs recognition and decides what is appropriate. No CV detector is bundled.

Typical category decisions:
- `cloud`: one-way `drift` / `motion: "advance"`; keep direction consistent with visible wind effects. A short local mask is suitable only for a few pixels; prepare a separate extended sky layer for substantial translation, masking all skyline objects.
- `foliage`: `breeze` / `motion: "oscillate"`; anchor trunks and vary phase/speed through separately designed effects rather than moving the whole tree rigidly.
- `vehicle`: `sprite` / `motion: "travel"` only for a car that should be driving, with clean plate, clear lane, coherent scale and reviewed tire contact/shadow. Parked vehicles remain fixed. A turning car needs view-dependent artwork, not translation of the same front view.
- `person`: travel plus >=4 full-canvas transparent registered poses and a `gait_review` describing feet/support, stride-to-travel agreement and pose continuity. Four frames alone do not prove a good walk. Prepare poses with the available image tool or a rig; inspect identity/clothing consistency. If this fails, report the missing action rather than substituting sliding or declaring the whole request complete.
- `fan`: separated rotor, fixed housing, `sprite` / `motion: "rotate"`, `direction: 1` or `-1`, and integer `cycles` turns per clip. Review aliasing and rotor edges; the fan grille remains in a foreground occluder mask.
- `gauge`: small sprite oscillation or deliberately supplied state poses; fixed dial, pivot at spindle and plausible needle limits. Do not spin the dial or invent readings as engineering results.
- `screen`: sprite `motion: "sequence"` with prepared content frames in the screen mask; subtle light variation may accompany it. Do not redraw surrounding console geometry or illegible random text every frame.
- `smoke`: `plume` / `motion: "flow"` from the identified exhaust, positive particle age and fade-out; no reversal. Local particle helper is stylized. More complex vapor needs prepared layers/provider.
- `light`: `motion: "advance"` for a progressive illumination change or `"oscillate"` for a justified indicator. Large day/night changes need shadows and lighting design; multiplying brightness alone is not a full time-of-day simulation.

Sprite travel fields: `path: [[0, dx0, dy0, scale0], ..., [1, dx1, dy1, scale1]]`, with strictly increasing normalized times and offsets measured from the source pose pivot. Include `path_review` for circulation, contact, perspective and entry/exit. Interpolation is piecewise linear; use sufficiently sampled gentle paths and do not cross walls or sidewalk furniture. All `sprite`, `clean_plate`, `removal_mask`, optional `occluder_mask` and `frames` are full-canvas PNG assets. The occluder mask's white pixels hide the moving layer behind fixed foreground parts; motion envelopes and protected masks still apply. The source object is removed before compositing the travelling layer. Frames are selected cyclically by `cycles` while position advances independently. The removal mask must cover the original object and any shadow being replaced; otherwise old silhouettes remain. For moving shadows, include them in prepared layers and review contact.

`timeline: "once"` samples start through end without a reset; a player may repeat it, but that does not make it seamless. `timeline: "loop"` rejects one-way drift/lighting and open travel paths rather than reversing time. Closed paths and periodic effects still need seam and velocity review. Continuous cloud wrap requires purpose-built seamless layers or a suitable separate renderer; crossfading a cloud backward is not a substitute. Existing r20 plans default to forward clips under this revision; explicitly request loop only for naturally periodic effects.
