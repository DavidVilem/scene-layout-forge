# Cross-subject style acceptance

Review the generated PNG against the same written art contract, regardless of client. Do not compare only equipment counts or the word "detailed" in a prompt.

1. Subject-specific silhouette and useful view: a station, room plan or machine reads as itself, not a renamed factory fixture.
2. Multiple scales of detail: large assemblies clear at fit view; actual joints, mounts, seams and functional controls visible closer. Hatch density alone does not pass.
3. Neutral paper/ink and coherent contour weights; no yellow tint or glossy shading unless explicitly requested.
4. Annotation policy: verify no explanatory text/arrows when not requested; when requested verify spelling, named component, visible arrowhead target and no text collisions. Honor requested language/count.
5. Required counts, contacts, access and poses checked on the output, not inherited from numerical reports. State hidden or unsupported evidence.
6. Setting explains scale, contact or use; the subject remains dominant. Respect explicit isolation/plan requests and avoid unsupported model, era or activity assumptions.
7. Variation follows function: urban forms and roof programs differ meaningfully; deliberate structural repetition remains coherent. A white void, clone grid or background that adds counted objects is not an automatic pass.

Use the examples as implementation patterns and the eval set as future tasks, not as a baked reference-image library. Record visual pass/fail per tested domain; success on one image is not proof that all technical subjects work. The generation model and environment can still introduce variation in VS Code or elsewhere.


## Detail acceptance is separate from count acceptance

At whole-image scale check hierarchy, chosen angle and clearance. Then inspect the planned focal regions at native pixel scale. Identify real secondary assemblies and readable junctions in each; do not count floor hatch marks, grain, repeated dots or more pixels as construction detail. Check that one detailed cabinet does not compensate for all other planned regions being empty or simplified. Clear windows and intentional quiet spaces are not failures.

Review label wording, hand-lettered character, arrowheads and exact targets independently. Inspect the arrow tip and nearby surfaces at native size; reject ambiguous tips on a person, guardrail or adjacent component. For mechanisms, review the visible transmission and load paths from mechanical coherence; attractive housings are not evidence that motion transfers correctly. Verify strong/medium/fine line hierarchy and restrained neutral shading. If planned construction detail is missing, request a targeted enrichment of those named regions while preserving camera, counts, connections and labels, within the existing maximum of two corrections. Do not automatically zoom in or change the scene to obtain detail. If the limit is reached, report which style requirement remains unmet.

For comparisons between clients, first compare the actual guide, finishing prompt, loaded revision, tool and image dimensions when available. Equal reasoning-model selections or equal user briefs do not establish identical generation inputs. Distinguish observed input differences from unproven explanations about the image service. Never certify cross-client equivalence from one successful image. Summarize the selected view, detail regions and style review in chat when the user requests deletion of all intermediate files.

For short requests, separately assess documented identity anchors, secondary assembly richness, contextual relevance and material-appropriate detail. A dense texture or correct label count cannot compensate for wrong proportions. See [planning](short-request-planning.md).
